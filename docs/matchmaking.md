# マッチング・CPU対戦・レート

認証有効時の通常プレイではレート対戦ロビーを表示します。
「マッチング開始」は人間を募集し、「CPUとすぐ対戦」は人間1人＋CPU4席で開始します。
どちらも全5局の最終順位でレートが更新されます。AI設定・AI対戦ログは従来通り管理者専用です。

## レート

- 人間はプレイヤーIDごと、CPUはplaying/bidding/nonPlayingの設定の組ごとにレート口座を持ちます。
- 初期レート1500。人間もCPUも同じ計算です。CPUの構成を変更すると別口座になります。
- 最終順位だけを使った5人用のペア比較Eloです。素点差・最終得点差は計算に使いません。
- 各相手との期待値 `E = 1 / (1 + 10^((相手レート − 自分レート) / 400))`。
- 最終順位が上ならS=1、同順位なら0.5、下なら0。各相手について `32 / 4 × (S − E)` を合計します。
- 同レートで同着なしなら1〜5位の変動は +16 / +8 / 0 / −8 / −16。内部は小数を保持します。
- 同じCPUが同卓に複数席ある場合、同一口座同士の比較は行わず、他の口座との各席の変動を口座に合算します。
  CPUの対戦数は参加した席の数で数えます。
- 1〜4局目は更新せず、5局目の結果確定時に自動更新します。画面の結果確認ボタンに依存しません。
- 完了済み試合は再送されても二重反映されません。CPUが別の卓に同時参加していてもDB内で口座をロックして更新します。

## マッチング

最も長く待っている人を基準にレート差400以内から近い人を最大5人集めます。
5人集まったら即開始。10秒経過したら残りを待機時に選んだCPUで埋めます。
募集処理はロビーの定期ポーリング時に実行します。CPUレートは選択肢に表示します。
待機中はキャンセル可能です。同一プレイヤーの重複待機・複数の進行中試合は作りません。

## API

| API | 内容 |
| --- | --- |
| GET /api/ratings/me | 自分のレートと参加数 |
| GET /api/cpus | 利用可能なCPUとレート |
| POST /api/matchmaking | 募集開始。任意のcpuIdで補充CPUを選択 |
| GET /api/matchmaking | 待機状態・進行中試合の再接続先 |
| DELETE /api/matchmaking | 待機キャンセル |
| POST /api/matchmaking/cpu | CPU4席との即時対戦 |
| GET /api/rated-matches/:matchId | 自分の手札・対戦状態・参加者・レート変動 |
| POST /api/rated-matches/:matchId/actions | 自席の操作。本文は旧ゲームAPIと同じ |
| POST /api/rated-matches/:matchId/next-trick | トリックを進める |
| POST /api/rated-matches/:matchId/next-round | 次局へ進める |

レート対戦の更新APIには取得した `competition.version` を `If-Match` ヘッダーで渡します。
古い状態からの更新は409で拒否し、画面は定期取得で最新状態に追従します。
対戦参加者だけが自分の手札を取得し、自席として操作できます。管理者も他人の席を操作できません。

## 保存・動作範囲

PostgreSQLの `rating_accounts` に口座、`rated_matches` に対戦状態、
`rating_results` に確定した順位・更新前後レートを保存します。
結果保存と全口座更新は同じトランザクションで行います。
サーバー再起動後は未完了試合を復元し、ロビーから戻れます。待機列はメモリ上なので再募集が必要です。

最初の構成はアプリサーバー1プロセスです。複数プロセスでの同一試合の進行共有は未対応です。
途中退出時のCPU代打・持ち時間は未実装のため、人間の操作待ちは再接続まで継続します。
途中で終わった試合には順位を付けず、レートを更新しません。
認証無効の開発モードでは既存の非レートCPU対戦画面を維持します。
